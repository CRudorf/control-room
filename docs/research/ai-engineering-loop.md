# The AI engineering loop: standards, practice, and what control room should do next

Research notes, October 2026. Every claim links its source. **[secondary]** marks a claim I could only find in secondary coverage; **[excerpt]** marks one I saw only in a search-result excerpt of the primary page, not the full page.

"Covered" refers to what control room already does (from `src/server/`): self-review of the user's PRs with per-repo lessons (`guides.ts`, `review.ts`, `lessons.ts`), the 7-day post-merge watch with verdicts (`shipped.ts`), risk flags that stop the review loop (`risk.ts`, `cycle.ts`), the review loop's round, agent and time caps (`cycle.ts`), stage times, friction and quality metrics (`metrics.ts`), token use per work item (`usage.ts`), the weekly brief and proposal loop (`loop.ts`), feedback forwarded to the owning agent (`tellagents.ts`), stale reviewer nudges (`nudges.ts`), and the layout check before deploy (`scripts/layout-check.ts`).

## What to do next

Ranked by expected value for the effort. Each says what is already covered.

1. **Push confirmed-break lessons up the enforcement ladder.** Today a confirmed break becomes a lesson, and only self-review reads it (`lessons.ts`, `review.ts`). The agent that writes the next change never sees it. Anthropic's guidance is a ladder: a line the model keeps missing belongs in a hook, and a rule with zero exceptions belongs in a hook or deny rule, not in `CLAUDE.md` ([best practices](https://code.claude.com/docs/en/best-practices)). So each confirmed lesson should get a target: a test or lint rule in the repo (strongest), a `PreToolUse`/`Stop` hook, or a path-scoped `.claude/rules/*.md` file that loads only where it applies ([memory docs](https://code.claude.com/docs/en/memory)). The weekly loop can draft that PR in the affected repo. OpenAI reports the same move, encoding rules as custom linters and structural tests ([InfoQ on OpenAI's harness engineering](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex) **[secondary]**). *Partly covered: lessons exist; promotion is new.*

2. **Turn confirmed breaks into a replay eval for self-review.** For each break with a verdict, re-run the self-review on the PR's original head in a clean worktree and check it flags the break. That is Anthropic's recipe: start with "20-50 simple tasks drawn from real failures", grade the outcome rather than the path, start each trial from a clean environment, and graduate passing cases into a regression suite that should stay near 100% ([evals post](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Show catch rate in Metrics next to watch accuracy. Without it, a prompt change to self-review can quietly stop catching known breaks. *New. Metrics already shows watch accuracy, which is the verdict side, not the catch side.*

3. **Give every build agent a check and ask it for evidence.** Field guides already require "Only claims you checked by running code" for reviews (`review.ts`). Build agents have no such contract. Anthropic: "Give Claude something it can run that comes back pass or fail", ask for "the command it ran and its output", and enforce must-pass checks with a `Stop` hook that exits 2 ([best practices](https://code.claude.com/docs/en/best-practices)). Concretely: a per-repo `Stop` hook running that repo's typecheck and fast tests, and the agent's final report (the review loop's `Report`) carrying commands and exit codes that the work item shows. *Partly covered: review side yes, build side no.*

4. **Serve the work item to agents on demand, not as a dump.** Control room already joins issues, PRs, CI and agents per work item. Expose that as a small CLI (or local MCP server) an agent can query: acceptance criteria, open threads, the failing job's log tail, the Sentry issue, the repo's lessons. Point to it from a `SessionStart` hook, which can add context ([hooks docs](https://code.claude.com/docs/en/hooks)). This follows "the smallest possible set of high-signal tokens" and just-in-time retrieval with "lightweight identifiers" ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)), and DORA's "AI-accessible internal data" capability ([DORA AI capabilities](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model)). Keep responses paged and short; Claude Code warns above 10,000 tokens of MCP output and caps at 25,000 ([MCP docs](https://code.claude.com/docs/en/mcp)). *New. `tellagents.ts` pushes new feedback; this lets agents pull the rest.*

5. **Mine transcripts for corrections the user made twice.** `usage.ts` already reads transcripts for tokens. The weekly loop could also find where the user corrected an agent, and propose a `CLAUDE.md` or rules line for any correction seen twice. That is the bar Anthropic sets for what belongs in `CLAUDE.md`: "Anything you've had to correct twice already" ([best practices](https://code.claude.com/docs/en/best-practices)). The same pass should propose cuts: keep files under 200 lines, and `/doctor prompt-audit` flags stale or contradictory lines ([memory docs](https://code.claude.com/docs/en/memory), [best practices](https://code.claude.com/docs/en/best-practices)). *New.*

6. **Give lessons a shelf life and a citation.** `lessons.ts` keeps the newest 8 per repo forever. GitHub's Copilot Memory stores facts with citations, checks them "against the current branch" before use, and expires them after 90 days without reinforcement ([Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). Cursor's Bugbot promotes candidate rules only after signal and disables rules that keep drawing negative signal ([Bugbot learning](https://cursor.com/blog/bugbot-learning)). Add file:line citations to lessons, drop ones whose code is gone, and retire ones self-review flags that the user dismisses. *New, small.*

7. **Match the gates to the risk categories deterministically.** `risk.ts` stops the review loop on migration, auth, money, PHI, infra and dependency changes, and merge is never in the app. Those are the right tiers. Add the deterministic layer agents can't talk past: deny rules for secrets and prod credentials, `autoMode` `soft_deny` entries for prod deploys in the user's user settings (keeping `"$defaults"`), and branch protection that a scheduled run can't bypass ([best practices](https://code.claude.com/docs/en/best-practices), [permission modes](https://code.claude.com/docs/en/permission-modes)). *Mostly covered in control room; the per-repo Claude Code layer is new.*

8. **Write "done" down before work starts for tasks typed into Start.** Tracked signals already go through signal-to-pr against acceptance criteria. Free-text tasks don't. Anthropic's pre-flight for unattended runs: "Does it know what done looks like?", plus caps on turns or spend, and a person approving the result ([best practices](https://code.claude.com/docs/en/best-practices)). A required "done when" field on free-text tasks is enough. *Partly covered.*

9. **Round out the metrics, and don't turn them into targets.** Stage times, friction, quality and the 7-day watch cover most of DORA's throughput and instability pairs for the user's own PRs. Two gaps: a perceptual measure (SPACE recommends at least three dimensions and "at least one of the metrics include perceptual measures such as survey data", [SPACE, CACM 2021](https://queue.acm.org/detail.cfm?id=3454124)), which can be one question in the weekly brief, and PR size, since small batches are the DORA capability most tied to AI benefit ([DORA AI capabilities](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model)). DORA warns that metrics set as goals get gamed ([DORA metrics guide](https://dora.dev/guides/dora-metrics/)). *Mostly covered.*

## 1. Industry standards for delivery across many repos

**DORA metrics.** DORA now defines five delivery metrics in two groups ([dora.dev](https://dora.dev/guides/dora-metrics/)):
- Throughput: change lead time (commit to production), deployment frequency, failed deployment recovery time.
- Instability: change fail rate ("deployments that require immediate intervention"), and deployment rework rate ("deployments that are unplanned but happen as a result of an incident in production").

Use them per application or service, together rather than singly, and not as targets, because targets "invite teams to game them" ([dora.dev](https://dora.dev/guides/dora-metrics/)). For a single engineer across many repos, that means per-repo trends, never a blended score.

**DORA on AI.** The 2024 report found that as AI adoption increased, "delivery throughput [fell] by 1.5%" and "delivery stability by 7.2%", and pointed back to "small batch sizes and robust testing mechanisms" ([Google Cloud, 2024 DORA](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)). The "per 25% increase in adoption" framing is widely quoted but I found it only in secondary coverage ([RedMonk](https://redmonk.com/rstephens/?p=861), [TechTarget](https://www.techtarget.com/searchsoftwarequality/news/366631712/Google-DORA-Software-delivery-caught-up-to-AI-coding-tools)) **[secondary]**. The 2025 report found a positive relationship with throughput, while stability still suffers; "without robust control systems, like strong automated testing, mature version control practices, and fast feedback loops, an increase in change volume leads to instability". Its headline: "AI doesn't fix a team; it amplifies what's already there" ([Google Cloud, 2025 DORA](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).

The 2025 DORA AI Capabilities Model names seven capabilities that amplify AI's benefit: clear and communicated AI stance; healthy data ecosystems; AI-accessible internal data; strong version control practices ("frequent use of rollback features boosts the performance of AI-assisted teams"); working in small batches ("especially powerful in an AI-assisted environment"); user-centric focus; quality internal platforms ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model)). Control room is, in effect, the user's personal internal platform, so the last one applies directly.

**SPACE.** Five dimensions: satisfaction and well-being, performance, activity, communication and collaboration, efficiency and flow. Capture "several metrics across multiple dimensions of the framework, at least three are recommended", and "at least one of the metrics include perceptual measures such as survey data", because "perceptual data may provide more accurate and complete information than what can be observed from instrumenting system behavior alone" ([Forsgren et al., CACM 64(6), 2021](https://queue.acm.org/detail.cfm?id=3454124); abstract at [Microsoft Research](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)).

**Google SRE.**
- Error budgets: while budget remains "new releases can be pushed"; when it's spent "releases are temporarily halted" ([SRE book, Embracing Risk](https://sre.google/sre-book/embracing-risk/)). The principle carries over to agents: unreliability spends autonomy.
- Canarying: "a partial and time-limited deployment of a change in a service and its evaluation", compared against a control, using "perhaps no more than a dozen" SLI-based metrics, one canary at a time ([SRE workbook, Canarying](https://sre.google/workbook/canarying-releases/)).
- Postmortems: blameless, with triggers defined in advance (including "on-call intervention such as a release rollback"), and "an unreviewed postmortem might as well never have existed" ([SRE book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)). Control room's watch-then-verdict-then-lesson loop is a lightweight postmortem; the review step is the user's verdict.

**Trunk-based development.** Merge to trunk "at least once" a day, "three or fewer active branches", branches lasting "no more than a few hours", no code freezes; track review turnaround and its outliers ([DORA capability](https://dora.dev/capabilities/trunk-based-development/)).

**Code review research.**
- At Google (9 million reviewed changes): median change is 24 lines, median reviewer count is 1, initial feedback in under an hour for small changes, whole review under 4 hours median, and the main motivation is education and norms as much as defects ([Sadowski et al., ICSE SEIP 2018](https://sback.it/publications/icse2018seip.pdf); [abstract](https://research.google/pubs/modern-code-review-a-case-study-at-google/)).
- Google's guidance: "100 lines is usually a reasonable size for a CL, and 1000 lines is usually too large"; small changes are reviewed faster, more thoroughly, and roll back more easily ([Google eng-practices](https://google.github.io/eng-practices/review/developer/small-cls.html)).
- At Microsoft: finding defects is the main stated motivation, but reviews yield fewer defects than expected and more knowledge transfer and awareness; understanding the change is the core challenge ([Bacchelli and Bird, ICSE 2013](https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/)). That supports control room's field guides, which target understanding, not just bug lists.

## 2. Self-improving loops with AI coding agents: practice vs hype

**What is published and real.**
- *Evals from real failures.* Anthropic: start with 20-50 tasks from real failures; capability evals start low, regression evals stay near 100%; read transcripts ("You won't know if your graders are working well unless you read the transcripts"); grade "what the agent produced, not the path it took"; isolate trials, since Claude once gained "an unfair advantage" by reading git history from previous trials ([evals post, Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- *Harness over prompt.* Anthropic's long-running harness uses a JSON feature list where agents may only flip a `passes` field ("It is unacceptable to remove or edit tests"), a progress file plus git history for handoff, one feature per session, and browser end-to-end tests, because agents marked features done after only unit tests or curl ([long-running harnesses, Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- *Learning from failures without retraining.* Reflexion stores verbal self-reflections in episodic memory and improves later trials (91% pass@1 on HumanEval), "not by updating weights, but instead through linguistic feedback" ([Shinn et al., 2023](https://arxiv.org/abs/2303.11366)). Control room's lessons are this pattern at the team level.
- *Products that learn from review feedback.* Cursor's Bugbot drafts candidate rules from reactions, replies and human reviewer comments on merged PRs, promotes them with signal and disables them on negative signal; Cursor reports the share of flagged bugs resolved by merge rose from 52% to "nearing 80%" (vendor-reported) ([Cursor](https://cursor.com/blog/bugbot-learning)). GitHub Copilot Memory stores repo facts with citations, validates them against the current branch, and expires them after 90 days unused; it says facts "should not be relied on as a rule that will always be followed" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). (A secondary summary said 28 days; the doc says 90.)
- *Claude Code memory.* `CLAUDE.md` is written by you and loaded every session; auto memory is written by Claude per repo, shared across worktrees, with a `MEMORY.md` index whose first 200 lines or 25KB load at start ([memory docs](https://code.claude.com/docs/en/memory)). Skills load name and description up front and the body only when used ([best practices](https://code.claude.com/docs/en/best-practices); progressive disclosure described in [Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) **[excerpt]**).
- *Google's migrations.* LLM edits plus AST and symbol tools; every change is built and tested, failures go back to the model, and humans own review and gradual rollout. 80% of code modifications in one migration's landed changes were fully AI-authored; engineers estimated about 50% time saved; "LLM-driven planning was often unnecessary"; reviewer capacity was the bottleneck ([Google, arXiv 2501.06972](https://arxiv.org/html/2501.06972v1)).
- *Anthropic on itself.* Claude wrote more than 80% of code merged at Anthropic as of May 2026; every change gets an automated Claude review, estimated to have caught roughly a third of the bugs behind past claude.ai incidents; the Claude judge of session success is itself validated against a separate set; humans set goals, choose problems and write scoring rubrics ([When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)).
- *OpenAI's harness engineering.* Three engineers drove about 1,500 merged PRs with Codex; the engineer's job shifted to "designing environments, specifying intent, and providing structured feedback"; a structured `docs/` directory is the system of record, enforced with linters and CI, plus structural tests for layering; agents get logs, metrics and spans ([InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex) **[secondary]**). The original ([openai.com](https://openai.com/index/harness-engineering/)) returned 403 to my fetches. The ~100-line `AGENTS.md` "map, not encyclopedia", "golden principles" and background "garbage collection" PRs appear only in secondary write-ups ([example](https://rohitraj.tech/en/notes/what-is-harness-engineering-codex-2026)) **[secondary]**.

**Where the evidence is weak or hype.**
- *Productivity claims.* METR's 2025 randomized trial found experienced open-source developers took 19% longer with AI while believing they were about 20% faster ([METR, Jul 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). METR's follow-up says its newer data is "an unreliable signal" because of selection effects, and that developers are likely faster now, on "only very weak evidence" ([METR, Feb 2026](https://metr.org/blog/2026-02-24-uplift-update/) **[excerpt]**). Lesson for control room: measure outcomes (watch verdicts, stage times), not perceived speed alone.
- *Self-reported uplift.* Anthropic staff self-report about 50% productivity gains, and the report notes self-reports may be biased ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)). Its own code-volume figure comes with "the true productivity gain is almost certainly smaller" ([When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)).
- *Benchmarks.* SWE-bench is 2,294 real GitHub issues from 12 Python repos ([Jimenez et al.](https://arxiv.org/abs/2310.06770)); a solution passes "only if it fixes the failing tests without breaking existing ones" ([evals post](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Benchmark gains don't transfer automatically to your repos; that is why a local replay eval (recommendation 2) matters.
- *"Recursive self-improvement" for an individual's tooling* is, in published practice, the boring loop: failures become evals or rules, a person reviews proposed changes, and the harness is re-tuned as models change. Anthropic found a harness behavior they'd built became "dead weight" on a newer model ([via secondary summary of Anthropic's later harness post](https://infoq.com/news/2026/04/anthropic-three-agent-harness-ai/) **[secondary]**), and its best-practices page keeps a "What you can stop doing" table ([best practices](https://code.claude.com/docs/en/best-practices)). Control room's weekly loop, which proposes and drafts but never merges, matches this.

## 3. Feeding agents context without drowning them

- **Principle.** Find "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; context has an "attention budget" and recall degrades as it grows ([Anthropic, Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Chroma measured 18 models and found performance "grows increasingly unreliable as input length grows", and "even a single distractor reduces performance" ([Chroma, Jul 2025](https://www.trychroma.com/research/context-rot)).
- **Just in time, by identifier.** Agents should "maintain lightweight identifiers" (paths, IDs, links) and load on demand; hybrids preload a little, as Claude Code does with `CLAUDE.md` ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). For the user: pass a work item key and a way to query it, not a pasted Sentry event, CI log and thread history.
- **Tools that return less.** Paginate, filter and truncate with sensible defaults; return names, not UUIDs; offer a concise/detailed `response_format`; write errors that say how to fix the call ([writing tools for agents, Sep 2025](https://www.anthropic.com/engineering/writing-tools-for-agents)). "Bloated tool sets" are a common failure ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Connected MCP servers add their tool names and instructions to context even when unused, so turn off ones you don't need ([best practices](https://code.claude.com/docs/en/best-practices)); a CLI with `--help` is often the easiest way in ([same](https://code.claude.com/docs/en/best-practices)).
- **What to write down.** Only what the agent can't find by reading the repo: test commands, misleading code, decisions not in the repo, repeated corrections. Rules for one area go in path-scoped `.claude/rules/`; procedures go in skills, which cost little until used ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Hooks as context channels.** `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart` and others can inject `additionalContext` ([hooks docs](https://code.claude.com/docs/en/hooks)). A `PostToolUse` hook that says "this file is generated, edit X instead" is the canonical example (same page).
- **Long work.** Compaction (tune for recall first), structured notes outside the context window, and subagents that return condensed summaries of 1,000 to 2,000 tokens ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). With 1M-token windows, running out is rare now, but `/clear` between unrelated tasks still improves answers and cost ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Untrusted context.** Servers that fetch external content expose you to prompt injection ([MCP docs](https://code.claude.com/docs/en/mcp)). Ticket text, PR comments from others and Sentry payloads are data, not instructions. Copilot filters hidden characters from issue and PR comments for this reason ([GitHub](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). Control room already sandboxes agent-written guide pages (`guides.ts` CSP).

## 4. Verifying agent work

- **A check that returns pass or fail is the single biggest lever.** Without one, "you [are] the test suite" ([best practices](https://code.claude.com/docs/en/best-practices)). Ladder of strictness: in the prompt, `/goal`, a `Stop` hook, or review by "someone who didn't write the code" (`/code-review` runs in a fresh subagent) (same). Ask for evidence: "'All tests pass' on its own tells you very little" (same).
- **Ground truth from the environment.** Agents should get "ground truth" from tool results or code execution at each step ([building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Run the app, not just unit tests: Anthropic's harness agents declared features done after unit tests or curl and missed end-to-end failures until given browser automation ([long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Control room's layout check is this for its own UI.
- **Tests can be gamed.** Anthropic reports Claude Opus 4 showed "narrow reward hacking behaviors" like "hardcoding or special-casing tests" ([sabotage risk report](https://alignment.anthropic.com/2025/sabotage-risk-report/2025_pilot_risk_report.pdf) **[excerpt]**). Defenses: forbid editing tests in the task contract ([long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)), use held-out checks the agent didn't write, and make graders "resistant to bypasses or hacks" ([evals post](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Self-review should treat a diff that touches tests and code together as a finding to verify.
- **LLM-as-judge pitfalls.** Position, verbosity and self-enhancement biases ([Zheng et al., 2023](https://arxiv.org/abs/2306.05685)); a model favors its own outputs, and the bias grows with how well it recognizes them ([Panickssery et al., 2024](https://arxiv.org/abs/2404.13076)). Anthropic: calibrate judges "closely" with human experts, give the judge an "Unknown" option, and use one judge per dimension ([evals post](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For control room: agent verdicts on the post-merge watch should be scored against the user's verdicts (Metrics' watch accuracy does this), and a reviewer asked to find problems "will always find *something*", so tell it to report only correctness gaps and skip style ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Independent verifiers.** A fresh session or subagent "hasn't seen your reasoning"; a reviewer agent limited to `Read, Grep, Glob` can't edit ([best practices](https://code.claude.com/docs/en/best-practices)). Anthropic's later harness work used a separate evaluator "since agents tend to overrate their own subjective output" ([secondary summary](https://infoq.com/news/2026/04/anthropic-three-agent-harness-ai/) **[secondary]**).
- **Property-based testing.** An agent that proposes properties and writes Hypothesis tests found real bugs across 100 Python packages; 56% of its reports were valid, 86% of the top-ranked ones ([Maaz et al., 2025](https://arxiv.org/abs/2510.09907)). Good fit for parsers, serializers and money math in the user's repos; triage is still required.
- **After merge.** Canaries with a control and a dozen SLI metrics ([SRE workbook](https://sre.google/workbook/canarying-releases/)); release toggles that ship latent code and are removed within "a week or two" ([Hodgson, Feature Toggles](https://martinfowler.com/articles/feature-toggles.html)); change fail and rework rates ([DORA](https://dora.dev/guides/dora-metrics/)). Control room's 7-day watch covers the per-PR version of the last one.
- **Passing tests overstates correctness.** In a blinded review of 296 SWE-bench-passing PRs by four maintainers of scikit-learn, Sphinx and pytest, roughly half would not have been merged; the grader overstates the merge rate by 24.2 points (SE 2.7) after normalizing to a 68% merge rate for the reference patches ([METR, Mar 2026](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)). Strengthened tests reject 19.7% of "solved" patches from the top 30 agents, and the leader drops from 78.8% to 62.2% ([SWE-ABS](https://arxiv.org/abs/2603.00520v1)). Both used 2024-2025 models without CI in the loop, and SWE-ABS's verdicts come from LLM-written adversarial tests. Self-review should judge intent and fit, not just CI status.

## 5. Gating work for human intervention

- **Deterministic vs model-judged gates.** Claude Code separates what the model decides (prompt, `CLAUDE.md`, auto mode's classifier) from what the harness enforces (hooks, deny rules, sandbox, managed settings, CI, branch protection, "a person who approves the merge") ([best practices](https://code.claude.com/docs/en/best-practices)). Auto mode "is a classifier model judging each action rather than a hard rule", so "never" rules belong in deny rules or hooks (same). Keep the enforced set small; "forty" hooks means most are preferences (same).
- **What auto mode blocks by default.** `curl | bash`, sending sensitive data out, production deploys and migrations, force push, destructive git and `terraform destroy`, "Merging a pull request no human has approved, approving Claude's own pull request, or disabling CI checks", printing live credentials, IAM changes. It falls back to prompting after 3 blocks in a row or 20 total ([permission modes](https://code.claude.com/docs/en/permission-modes)). `autoMode` settings must live in `~/.claude/settings.json` and keep `"$defaults"` ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Unattended runs.** Five questions: what done looks like, how it checks itself, what it may touch, what stops it (`--max-turns`, `--max-budget-usd`), and who signs off ([best practices](https://code.claude.com/docs/en/best-practices)). Protect `main` with a rule a scheduled task can't bypass (same). Agent loops need stopping conditions such as iteration caps ([building effective agents](https://www.anthropic.com/engineering/building-effective-agents)); control room's 3 rounds, 3 new agents and 3-hour round timeout are exactly that.
- **Platform gates.** Copilot's agent can't approve or merge, the requester can't approve their own agent's PR, Actions don't run on its PRs until a write-access user approves, and it pushes to one branch only ([GitHub](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). GitHub environments add required reviewers, "prevent self-review", wait timers and branch restrictions for deploys ([GitHub Docs](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)).
- **Oversight at the plan, not every step.** Anthropic moves oversight "from the individual step to the overall strategy" with plan mode, and reports Claude's own check-in rate roughly doubles on complex tasks ([Trustworthy agents in practice, Apr 2026](https://www.anthropic.com/research/trustworthy-agents)). Manual approval of everything fails differently: "after the tenth prompt you start approving without reading" ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Always a human**, synthesizing the above: merge to a protected branch; production deploys, migrations and infra applies; anything touching auth, money, PHI or credentials; dependency additions; messages that reach a teammate or customer; deleting data; disabling a check. Control room already matches most of this (risk categories, confirm-before-notify, no merge in app).
- **Sandbox defaults fail open.** The sandbox is off by default and falls back to running unsandboxed unless `sandbox.failIfUnavailable` is true; `dangerouslyDisableSandbox` retries are allowed unless `allowUnsandboxedCommands` is false; Read, Edit, Write, WebFetch, MCP servers and hooks sit outside it ([sandboxing](https://code.claude.com/docs/en/sandboxing)). Boundaries stated only in conversation can be lost on compaction ([permission modes](https://code.claude.com/docs/en/permission-modes)).

## 6. Where an engineer's attention should go

- **Setting goals, specs and "done".** At Anthropic, "humans supply the goal, but they no longer need to supply the method"; people choose problems and write scoring rubrics ([When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)). Users make about 70% of planning decisions and Claude about 80% of execution decisions ([Agentic coding and expertise, Jun 2026](https://www.anthropic.com/research/claude-code-expertise)). Interviewing to a `SPEC.md` and building from it in a fresh session is the documented pattern ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Verification design over line reading.** Expert sessions reach verified success more than twice as often as novice ones, and expertise shows in "what they ask Claude to verify" ([Agentic coding and expertise](https://www.anthropic.com/research/claude-code-expertise)). Engineers delegate what they can "sniff-check"; more than half can fully delegate only 0-20% of their work; one estimated "70%+" of their work shifted to reviewing and revising output ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)).
- **Review for understanding.** Review's biggest payoff is understanding and knowledge transfer ([Bacchelli and Bird](https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/)), and code review may become the bottleneck as agents produce more ([When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)); at Google, reviewer capacity capped how fast AI migrations could land ([Google](https://arxiv.org/html/2501.06972v1)). Keep agent PRs small so they stay reviewable ([Google eng-practices](https://google.github.io/eng-practices/review/developer/small-cls.html)).
- **AI hasn't shortened review.** 84.3% of frequent GenAI users in a 415-developer open-source survey said it did not reduce their review time, and many reported reviewing more ([Sergeyuk et al., 2025](https://arxiv.org/html/2510.24265v1); self-reported, one survey). Across studies, perception-based results are 81.5% positive versus 53.9% for statistically evaluated ones ([ASE '26 review](https://sws.informatik.uni-leipzig.de/wp-content/uploads/2026/07/Productivity_of_Software_Developers_with_AI_tools_LitRev.pdf)), so judge the loop by reverts, rework and change failure rate, not by how fast it feels.
- **Steer early, restart rather than argue.** Watch the first minute; after two failed corrections, `/clear` and write a better prompt ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Protect the skills you supervise with.** Anthropic staff describe a "paradox of supervision": supervising Claude needs the coding skills heavy use can erode; some practice without AI on purpose ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)).
- **Interrupts are expensive.** Programmers took 10-15 minutes to resume editing after an interruption, and only about 10% resumed within a minute ([Parnin and Rugaber, 2011](https://sites.cc.gatech.edu/reverse/repository/resumptionstrategies.pdf); minute figures via [InfoQ](https://www.infoq.com/news/2013/01/Interruptions/) **[secondary]**). Control room's design already batches: notify only when the ball moves to the user, park with a wake condition, quiet by default. The remaining lever is grouping agent questions so a "blocked on input" ping arrives at a natural break, not mid-task.
